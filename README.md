# CRSFJoystick

Прошивка для плат **RP2040**, яка перетворює приймач **ExpressLRS / CRSF / Tracer**
на **USB HID-геймпад** для симуляторів.

Плата спілкується з приймачем протоколом CRSF, а вхідні канали віддає як осі та
кнопки джойстика через нативний USB. Назва *CRSFJoystick* походить саме від цього
протоколу.

* 16 аналогових каналів (канали 1–16) → X, Y, Z, Rx, Ry, Rz, Slider, Dial,
  Wheel, Axis9..Axis15 (X=roll, Y=pitch, Z=throttle, Rx=yaw; порядок
  осей = порядок каналів)
* Канали 15–16 теж задіяні за замовчуванням — у повному режимі ELRS
  (Full Res 16ch) це звичайні AUX11/AUX12. Якщо ваш режим ELRS несе на цих
  слотах LQ %/RSSI %, закоментуйте `MAP_SIGNAL_AXES` (див. `calibration.h`)
* Кнопки положень AUX-перемикачів (канали 5–16 → кнопки 0–35; HID підтримує до 128)
* Failsafe: при втраті звʼязку всі осі центруються, а кнопки відпускаються
  (стан повторюється кожні 100 мс)
* Основний таргет — ExpressLRS; TBS Crossfire і TBS Tracer також працюють

  полярність живлення самостійно.

## Підтримувані плати

Кожна плата — окреме середовище PlatformIO (див. `platformio.ini`). Прапорець
збірки `BOARD_ID` вибирає відповідну мапу пінів/LED у `include/board_defs.h`.

| Середовище PlatformIO | Плата                    | BOARD_ID | MCU TX | MCU RX |
| --------------------- | ------------------------ | -------- | ------ | ------ |
| `pico`                | Raspberry Pi Pico        | 1        | GP4    | GP5    |
| `tiny2040`            | Pimoroni Tiny 2040       | 2        | GP4    | GP5    |
| `waveshare2040zero`   | Waveshare RP2040-Zero    | 3        | GP4    | GP5    |
| `seeedxaio2040`       | Seeed XIAO RP2040        | 4        | GP0    | GP1    |
| `qtpy2040`            | Adafruit QT Py RP2040    | 5        | GP20   | GP5    |

## Підключення приймача (розпіновка дротів)

Покрокова інструкція для кожної плати — у
**[`docs/wiring.md`](docs/wiring.md)**. Там показано, як і куди паяти дріт:

* **офіційний пінаут плати** — як фізично виглядає ваша плата і де який контакт;
* **схема зʼєднань** — який дріт куди йде, з кольоровою підказкою
  (🟢 TX, 🔵 RX, 🔴 5V, ⚫ GND);
* **таблиця** — який саме напис шукати на платі (`GP4`/`GP5`, `D6`/`D7`,
  `TX`/`RX`, `5V`, `GND`) і на який контакт приймача його підключити.

Памʼятайте: CRSF — це повнодуплексний UART, тому сигнальні лінії перехрещуються
(**MCU TX → RX приймача**, **MCU RX → TX приймача**).

## Готові прошивки (без встановлення PlatformIO)

Якщо не хочете встановлювати VSCode + PlatformIO і збирати прошивку самостійно —
візьміть уже готовий файл `.uf2` для своєї плати зі сторінки
**[Releases](https://github.com/realwarrior3/CRSFJoystick/releases)**:

| Плата                      | Середовище          | Файл у релізі             |
| -------------------------- | ------------------- | ------------------------- |
| Raspberry Pi Pico          | `pico`              | `pico.uf2`                |
| Pimoroni Tiny 2040         | `tiny2040`          | `tiny2040.uf2`            |
| Waveshare RP2040-Zero      | `waveshare2040zero` | `waveshare2040zero.uf2`   |
| Seeed XIAO RP2040          | `seeedxaio2040`     | `seeedxaio2040.uf2`       |
| Adafruit QT Py RP2040      | `qtpy2040`          | `qtpy2040.uf2`            |

Як прошити (метод BOOTSEL / UF2):

1. Затисніть кнопку **BOOTSEL** і, утримуючи її, підключіть плату до USB
   (або, якщо плата вже живиться, натисніть BOOTSEL + RESET).
2. Зʼявиться змінний диск (наприклад `RPI-RP2`).
3. Перетягніть потрібний `.uf2` на цей диск.
4. Плата перезавантажиться й зʼявиться як геймпад.

> Прошивки в релізах відповідають певному стану коду. Якщо потрібна найновіша
> версія — зберіть прошивку з джерел самостійно (див. нижче).

## Встановлення VSCode + PlatformIO

1. Встановіть Visual Studio Code: <https://code.visualstudio.com/>
2. У VSCode відкрийте панель розширень (`Ctrl+Shift+X`), знайдіть
   **PlatformIO IDE** і встановіть його.
   (Повна інструкція: <https://platformio.org/install/ide?install=vscode>)
3. Перезапустіть VSCode та відкрийте цю теку: `File → Open Folder…`

Під час першої збірки PlatformIO автоматично завантажить тулчейн для RP2040.

## Збірка та прошивка

Панель PlatformIO розташована внизу вікна VSCode.

1. **Виберіть плату.** Клацніть назву середовища (спочатку
   `Default (CRSFJoystick)`) на панелі та виберіть свою плату
   (`pico`, `tiny2040`, `waveshare2040zero`, `seeedxaio2040`, `qtpy2040`).
2. **Збірка.** Натисніть кнопку **✓** (галочка).
3. **Прошивка.** Підключіть плату по USB і натисніть кнопку **→** (стрілка).

### Оптимізація

* HID-звіт надсилається лише коли стан змінився і не частіше одного разу на
  мілісекунду (це `bInterval` USB-ендпоінта) — у спокійному стані USB не
  займається передаванням незмінних даних.

### Зміна назви USB-пристрою (опційно)

За замовчуванням у системі пристрій зʼявляється як `RaspberryPi Pico` — ця назва
зашита в спільний фреймворк PlatformIO. Якщо хочете власну назву (наприклад,
`CRSFJoystick`), є **opt-in** скрипт, вимкнений за замовчуванням:

1. Відкрийте [`scripts/usb_product_name.py`](scripts/usb_product_name.py) і
   впишіть бажану назву в константу `USB_PRODUCT_NAME` (порожній рядок = нічого
   не змінювати).
2. У `platformio.ini` розкоментуйте рядок у секції `[env]`:
   `extra_scripts = pre:scripts/usb_product_name.py`
3. Зберіть прошивку як завжди.

Нічого додатково встановлювати не потрібно, зокрема **Python**: скрипт виконується
тим самим Python, який постачається разом із PlatformIO (власне середовище
`~/.platformio/penv`), тож окремо встановлювати Python не треба. Під час збірки
скрипт робить локальну копію варіанта фреймворку (у `.pio/`) з підміненим рядком
`BOARD_NAME`, а сам спільний фреймворк не змінюється. Якщо рядок у `platformio.ini`
закоментований (типово) — скрипт не використовується взагалі.

> Назву бажано писати лише ASCII (латиниця, цифри, пробіли): кирилиця в
> USB-дескрипторі може відображатися некоректно.
>
> Windows може кешувати стару назву пристрою. Щоб побачити нову, видаліть
> пристрій у Диспетчері пристроїв (разом із драйвером) і підключіть знову.
>
> Якщо VSCode (розширення Python) запропонує вибрати інтерпретатор — це лише для
> підсвічування коду (IntelliSense) і на збірку не впливає: запит можна закрити.
> За бажанням вкажіть `~/.platformio/penv/Scripts/python.exe`.

### Альтернативне прошивання (BOOTSEL / UF2)

Це стандартний метод для плат Raspberry Pi, який не потребує додаткових
інструментів:

1. Затисніть кнопку **BOOTSEL** і, утримуючи її, підключіть плату до USB
   (або, якщо плата вже живиться, натисніть BOOTSEL + RESET).
2. Зʼявиться змінний диск (наприклад `RPI-RP2`).
3. Перетягніть файл `firmware.uf2` з теки `.pio/build/<env>/` на цей диск
   (замініть `<env>` на назву середовища вашої плати). Якщо ви не збирали
   прошивку самостійно — візьміть готовий `.uf2` зі сторінки
   [Releases](https://github.com/realwarrior3/CRSFJoystick/releases)
   (див. розділ «Готові прошивки» вище).
4. Плата перезавантажиться й зʼявиться як геймпад.

### Драйвери (Windows)

USB-драйвер RP2040 інколи погано дружить із PlatformIO. Якщо прошивка не може
знайти плату, можливо, доведеться замінити драйвер через Zadig:
<https://github.com/platformio/platform-raspberrypi/issues/2#issuecomment-828586398>

Перевірене на Windows 11 зіставлення драйверів:

| Режим          | Інтерфейс | Драйвер у Zadig | Диспетчер пристроїв                                                        |
| -------------- | --------- | --------------- | -------------------------------------------------------------------------- |
| Звичайна робота | 0         | HidUsb          | Human Interface Devices → HID-compliant game controller                     |
| Звичайна робота | 1         | usbser          | Ports (COM & LPT) → USB Serial Device                                       |
| RP2 Boot       | 0         | USBSTOR         | Disk Drives → RPI RP2 USB Device                                            |
| RP2 Boot       | 1         | WinUSB          | Universal Serial Bus Devices → RP2 Boot                                     |

Щоб змінити драйвер: клацніть пристрій правою кнопкою → Properties →
Update Driver → Browse my computer → Let me pick from a list of available drivers.

## Після прошивання

* Звʼяжіть приймач зі своїм пультом. Вбудований LED показує стан звʼязку
  (світиться = є звʼязок, блимає = немає звʼязку).
* Налаштуйте ELRS на режим **Full Res 16ch** — інакше канали 13/14 не
  працюватимуть коректно (див. розділ нижче, це вимога саме ELRS, а не прошивки).
* Перевірте пристрій у тестері геймпадів, наприклад
  <https://hardwaretester.com/gamepad>.

## ⚠️ Налаштування ELRS: потрібен режим «Full Res 16ch»

Прошивка очікує всі 16 каналів, але **не всі режими перемикачів ELRS їх
передають** (див. [Switch Configs](https://www.expresslrs.org/software/switch-config/)):

* **Hybrid / Wide / Full Res 8ch / Full Res 12ch Mixed** — канал 13 взагалі
  **не передається** по повітрю (геймпад на ньому нічого не бачить), а в ELRS v4
  канал 14 свідомо **дзеркалить перемикач озброєння (ARM)** — Axis 13 і кнопки
  27–29 при цьому дублюють CH5/AUX1. Крім того, у Hybrid/Wide канали 15/16 несуть
  LQ/RSSI замість ваших значень.
* **Full Res 16ch Rate/2** — усі 16 каналів передаються як звичайні незалежні
  значення, і вся мапа цього проєкту працює як задумано.

Якщо ви з якоїсь причини лишаєтесь на Hybrid/Wide — закоментуйте
`MAP_SIGNAL_AXES` в [`include/calibration.h`](include/calibration.h), щоб LQ/RSSI
не потрапляли на осі Axis14/Axis15 і кнопки 30–35.

Як увімкнути (ELRS Lua-скрипт на апаратурі; згідно з документацією ELRS — коли
передавач не озброєний):

1. **Packet Rate → 100Hz Full** або **333Hz Full** (повнорежимні режими
   працюють тільки на цих швидкостях);
2. **Switch Config → Full Res 16ch Rate/2**.

Обмеження режиму: швидкість пакетів 100/333 Гц, канали 5–16 оновлюються на
половинній швидкості (Rate/2), діапазон значень 885–2115 мкс (CRSF Ext Limits —
вікна калібрування прошивки це враховують). Без цього налаштування канали 13/14
працювати коректно не будуть — і це особливість стандарту ELRS, а не збій
прошивки.

## Мапа каналів (CRSF → USB HID)

Протокол CRSF визначає лише транспорт і значення каналів (16 каналів по 11 біт,
172–1811 = 987–2012 мкс, центр 992 = 1500 мкс). Він **не** нормує, як канали
лягають на осі USB-HID — це вирішує прошивка. Наш мапінг призначає канали 1–16 на
осі по зростанню HID usage 0x30..0x3F (X, Y, Z, Rx, Ry, Rz, Slider, Dial, Wheel,
Axis9..Axis15), тому індекси осей у тестерах збігаються з номерами каналів
(X=roll, Y=pitch, Z=throttle, Rx=yaw):

| Канал | Призначення (EdgeTX/ELRS)   | Вісь HID | Кнопка HID (LOW / MID / HIGH) |
| ----- | --------------------------- | -------- | ----------------------------- |
| 1     | A — Aileron (Roll)          | X        | —                             |
| 2     | E — Elevator (Pitch)        | Y        | —                             |
| 3     | T — Throttle                | Z        | —                             |
| 4     | R — Rudder (Yaw)            | Rx       | —                             |
| 5     | AUX1 (в ELRS — Arm)         | Ry       | 0 / 1 / 2                     |
| 6     | AUX2                        | Rz       | 3 / 4 / 5                     |
| 7     | AUX3                        | Slider   | 6 / 7 / 8                     |
| 8     | AUX4                        | Dial     | 9 / 10 / 11                   |
| 9     | AUX5                        | Wheel    | 12 / 13 / 14                  |
| 10    | AUX6                        | Axis 9   | 15 / 16 / 17                  |
| 11    | AUX7                        | Axis 10  | 18 / 19 / 20                  |
| 12    | AUX8                        | Axis 11  | 21 / 22 / 23                  |
| 13    | AUX9                        | Axis 12  | 24 / 25 / 26                  |
| 14    | AUX10                       | Axis 13  | 27 / 28 / 29                  |
| 15    | AUX11 (у Hybrid/Wide ELRS — LQ %)   | Axis 14  | 30 / 31 / 32                  |
| 16    | AUX12 (у Hybrid/Wide ELRS — RSSI %) | Axis 15  | 33 / 34 / 35                  |

Примітки:

* Канали 1–16 віддаються як аналогові осі; канали 5–16 додатково керують кнопками
  положень (по три кнопки — LOW/MID/HIGH — на кожен перемикач, усього 0–35).
* Індекс осі в браузерних тестерах визначається HID usage-кодом, а Chromium/Edge
  застосовують правило `index = usage - 0x30`. Тому всі 16 осей дескриптора
  оголошені usage-ами 0x30..0x3F (X=0, Y=1, Z=2, Rx=3, Ry=4, Rz=5, Slider=6,
  Dial=7, Wheel=8, Axis9=9 … Axis15=15) і канали 1–16 лягають на **фіксовані**
  індекси 0–15 без «стрибків».
* Хати (D-pad) у дескрипторі відсутні — цей форк їх не використовує. За потреби
  D-pad легко емулювати чотирма кнопками.
* Пороги кнопок AUX: LOW 800–1250 мкс, MID 1350–1650 мкс, HIGH 1750–2200 мкс
  (див. [`include/calibration.h`](include/calibration.h)).
* У режимах ELRS канал 5 зазвичай використовують як Arm (2-позиційний) — тоді
  середня кнопка (MID) на ньому ніколи не спрацює, і це нормально.
* Канали 15/16 задіяні за замовчуванням (осі Axis14/Axis15 + кнопки 30–35):
  у режимі Full Res 16ch це звичайні AUX11/AUX12. Якщо ваш режим ELRS несе на
  них LQ/RSSI (Hybrid/Wide), закоментуйте `MAP_SIGNAL_AXES` — інакше телеметрія
  «ворушитиме» ці осі та кнопки.
* Осі стіків (канали 1–4) можна перепризначити у симуляторі; жорсткого стандарту
  «який канал = яка вісь HID» у CRSF/ELRS не існує.

## Калібрування та призначення

Межі каналів і мапа кнопок задаються у [`include/calibration.h`](include/calibration.h);
коментарі в цьому файлі пояснюють, як додавати чи прибирати привʼязки. Піни під
кожну плату та робота з LED — у [`include/board_defs.h`](include/board_defs.h).

### Діагностика (опційно)

У `src/main.cpp` є два закоментовані макроси для налагодження через Serial
Monitor плати (іконка Serial Monitor у панелі PlatformIO або
`pio device monitor`):

* `BTN_PRINT` — друкує id кнопки, значення каналу (µs) і стан щопакета
  (швидко заливає порт — вмикайте лише короткочасно).
* `CH_PRINT` — друкує сирі значення каналів 5/13/14/15/16 і розмір кадру CRSF
  лише при зміні (`fs=24` = повний 16-канальний кадр). Допомагає відрізнити
  проблему «у даних від радіо» від проблеми «у хості/дескрипторі» та визначити
  режим ELRS (якщо ch15/ch16 бігають 0..100 % — це LQ/RSSI, тобто не Full Res 16ch).

### Версії вбудованих бібліотек

Обидві бібліотеки в `lib/` — це копії upstream, синхронізовані з такими
станами (з кількома локальними виправленнями, описаними нижче):

* `lib/CrsfSerial` — стан CRServoF на 2026-01-21. Локальні відхилення:
  `queuePacket()` знову приймає необов'язковий параметр адреси, щоб reboot-команда
  для приймача йшла на `CRSF_ADDRESS_CRSF_RECEIVER` (0xEC), як було до зміни API
  в upstream (там адресу жорстко зашито в `CRSF_SYNC_BYTE` = 0xC8); та додано
  гетер `getFrameSize()` (розмір останнього обробленого кадру) — для діагностики
  `CH_PRINT`.
* `lib/PicoGamepad` — стан PicoGamepad на 2025-04-28 (16 осей) з локальними
  змінами: хати (D-pad) повністю прибрані з дескриптора й коду (їх не
  використовує жоден таргет), а осі 9–15 оголошені usage-ами 0x39..0x3F замість
  0x40..0x46 — щоб усі індекси осей були фіксовані у Chromium/Edge (див. «Мапа
  каналів» вище). Крім цього: перевірка меж у `SetButton()` (`>= 128`), обнулення
  `inputArray` у конструкторі та видалений некоректний usage «System Undefined».
  Додатково додано `getInputs()` і `INPUT_BYTES` — щоб `main.cpp` міг визначати,
  чи стан змінився, перш ніж надсилати HID-звіт.
